# Governed IDE harness

The Theia frontend is a client of `/services/governed-tasks`. Execution, workflow state, tools and permission checks live in the backend. Browser reloads do not interrupt a run. One backend owns the SQLite runtime; only one running/action-approval run is allowed per task.

## Modules

- `core/contracts.ts`: provider, store, tool, policy and output interfaces; explicit tool registration.
- `core/tool-access.ts`: tool-owned category declarations and the policy evaluation contract; no central switch on tool names.
- `storage/tool-policies.ts`: evaluates embedded tool policies and authorization revisions. `ToolsWidget` edits complete manifests through the project Tools service.
- `core/runtime.ts`: sequential dispatch, cancellation, bounded provider turns, persistence and exact action approvals.
- `core/workflow-engine.ts`: workflow snapshots, prerequisites, step results, block/review states, explicit approval and invalidation.
- `core/context.ts`: task instructions and compact selective architecture memory.
- `core/task-context.ts`, `task-memory-history.ts`, `task-result-view.ts`: token budgeting, bounded result views, incremental task checkpoints and complete protocol boundaries.
- `modules/task-memory-tools.ts`: task-scoped search and paged retrieval of canonical messages/results.
- `storage/sqlite-store.ts`: SQLite transactions/WAL, messages, actions, interactions, authorization grants, events and crash recovery. Workflow snapshots/results are persisted in the owning task body.
- `storage/mutation-queue.ts`: serialization of this backend's project mutations and shared physical repository checkouts.
- `modules/repository-tools.ts` and `modules/file-tools.ts`: registered-root discovery/search and bounded batch file reads.
- `modules/git-tools.ts`: bounded Git inspection/diff and clean feature-branch creation.
- `modules/changesets.ts` and `modules/write-tools.ts`: project Markdown plans, separate execution notes and guarded repository edits.
- `modules/project-memory.ts` and `modules/memory-tools.ts`: selective durable architecture memory, reviewed merge/update and system research.
- `modules/openai-provider.ts`: direct Responses transport through the existing ChatGPT connection; no Codex harness or model-owned terminal.
- `storage/project-tools.ts` and `project-tool-service.ts`: declarative project tool definitions, approved proposals and project-scoped callable function registration. `/services/project-tools` is the frontend API.
- `core/execution.ts`, `execution-service.ts`, `storage/executions.ts`: execution adapter registry, durable generic runs, cancellation and history.
- `executors/local-process.ts`: the first adapter, fixed native commands scoped to connected repository working folders.
- `task-service-impl.ts`: RPC and module composition.

## Project files and local storage

`project.theia-workspace` is required by Theia. It contains `governedProject` metadata and authoritative `governedRepositories` registration. Old generated `project.yaml` and `repos.yaml` files are consolidated and removed when opening an old project; edits to the old repository YAML never changed live registration.

New projects create `changesets/`, `tools/`, `context/`, `repositories/` and `workflows/`. Old projects create `tools/` on first use. Repository folders are registered links to external checkouts; registration and link targets must agree. Workflow definitions live in `workflows/<id>.json`; Development keeps `development.json`.

The database is `~/.governed-ide/runtime/tasks.sqlite`. It is global storage partitioned by canonical project path and task ID, outside repository checkouts; it is not encrypted at rest. Authentication remains in the connection service. Drafts and submitted-message IDs persist. Browser selection/layout preferences remain browser-local.

## Workflow execution in chat

Workflow schema v5 stores an explicit `tools` array of stable project manifest IDs on every step. The editor provides a searchable Tools selector, selected count and unavailable references. New steps start with no selected tools. Development ships with focused, independently editable selections per step. There is no wildcard or automatic inclusion of newly installed/proposed tools.

The selector displays added tools as removable rows above a searchable dropdown; selected tools are excluded from the results. There is no separate step-level operations list. Trusted installed executors declare internal `workflowOperations` metadata for the workflow guards they support; handler bindings preserve it. Workflow authorization derives these capabilities from the current step's selected, available tools. Ready criteria, approved ChangeSet digests/scope, prepared branches, original-content checks and per-tool policies remain enforced. These handler capabilities are implementation metadata, not another configurable permission source.

`WorkflowToolScope` is the shared boundary for provider schemas and runtime dispatch. It resolves manifest IDs rather than mutable function names, intersects them with handler availability, and rechecks the current step before preparation, execution and deferred proposal responses. Changing steps replaces the schema set and revokes access from the preceding step. Normal chat and background repository analysis retain their existing behavior. Access rules, registered paths, Ready/Done and ChangeSet guards remain independent restrictions.

Canonical installed question, task-memory and workflow-control executors declare `workflowSupport` metadata. These are shown separately as always available so an empty step can recover task details, ask questions and report/advance. Their policies still apply. Handler aliases do not inherit automatic inclusion; their manifest IDs must be selected explicitly. Workflow documents use schema v5; the task database uses schema v6. Existing running tasks still use their saved selections; editing a workflow affects newly selected tasks.

New chats have no workflow selector. Sending the first message starts a routing turn; only Workflow.route and Ask user are exposed and permitted at dispatch. The model recommends a saved workflow (or ordinary chat) with a reason. Workflow.route creates a durable workflow_selection interaction with the recommendation, all available nonempty workflows and Continue without workflow. It does not start a process. The user must click a specific option; ordinary text and model recommendations never count as selection. A user can choose a different workflow from the recommendation. Only then is the chosen definition snapshotted and activated, and the same run resumes with its step-scoped tools. Choosing chat resumes ordinary conversation instead. Selection survives recovery, respects tool policy, rejects stale/cancelled requests and accepts identical responses idempotently. System repository analysis bypasses routing. Later project definition edits do not alter active task snapshots. There is one workflow execution per task.

`workflow_ready` records all prerequisites; unmet prerequisites block the step. `workflow_report` accepts only a technical blocker or a completed step result. Questions use `ask_user` and are independent of step results. A user answer resumes the same step. Plain model prose never silently finishes a workflow step: without a control report, the run waits for input.

A completed result includes every Done criterion and evidence references. References must identify an actual user message or successful action in this task. Statuses are met, unmet and not_applicable, with explanations. Text criteria are still agent assessments: reference existence is checked, semantic correctness of every claim is not formally proven. The UI states this explicitly.

Steps with user confirmation pause in Review required. **Approve and continue** applies to the exact pending result revision and its saved ChangeSet plan digests. Ordinary chat text, including “yes” or “approve”, is feedback rather than approval. A changed plan cannot be approved using an old review result. `workflow_revise` reopens an earlier step and invalidates its later results/approvals. Completed workflows require a new task for further work.

Step operation permissions are explicit and editable: changeset-write, branch-create, repository-edit, memory-update. Merely writing an instruction does not enable a mutation. Repository mutations additionally require a previously approved ChangeSet authorizing the repository and exact file path. The engine does not hard-code Development stage IDs.

The Development template has seven stages: understand (confirmation), study, prepare ChangeSet (confirmation), prepare feature branches, implement, verify and update memory. Existing project-owned definitions are independent copies. The current project was explicitly updated at the user's request; other saved workflows are not silently replaced.

## Tools and boundaries

| Tools | Boundary |
| --- | --- |
| repositories_list / repository_list / repository_search | Registered repositories only; bounded inventory and literal search |
| files_read | 1–20 UTF-8 files, 64 KiB each, 90,000 output characters; registered repository reads automatic, other project files need approval |
| git_status / git_diff | Registered Git roots only; structured changes and bounded patches; no user-supplied Git command/options |
| git_branch_create | Ready permitted step, approved repository scope, clean tree, unchanged HEAD/status, agreed default or explicitly scoped base; creates a new branch at the same commit |
| changeset_list / changeset_read | Markdown filenames directly in project ChangeSets/ |
| changeset_write | Ready permitted step; exact repository/file scope; expected digest or null for create |
| changeset_notes | Replace execution notes in an approved plan; plan body/scope remain unchanged |
| repository_edit | One exact approved UTF-8 path, prepared task feature branch, expected source digest; create/replace/delete |
| context_index / context_get | Compact index and one or two selected architecture topics |
| repository_analyze / context_publish | Separate hidden system research, own repository only; existing-memory refresh requires review in Project Context |
| context_update | Read affected current topics and source first, explain durable value, propose merge/retirements; action review required |

Git commands use fixed argument lists, a sanitized Git environment, explicit git-dir/work-tree, disabled hooks/fsmonitor/pager/external-diff/textconv and no network commands. Redirected/symbolic Git metadata, external config includes/alternate object stores and linked-worktree layouts are rejected. Git metadata inspection is bounded to 30,000 entries. Remote freshness is not claimed: tools inspect local references. An unexpected or dirty base requires user resolution; no automatic reset, stash, existing-branch checkout, commit, push or merge is exposed.

The preceding paragraph describes the original scoped helpers. The universal `git` tool now also accepts a subcommand/argument array, including native switch, fetch and rebase. It shares root/metadata validation, uses a bounded native-process adapter, and requests policy-based permission. The scoped branch-creation helper remains because it records the approved feature branch in the workflow. Existing task branches never change automatically.

## Tool modules and project policies

`ToolModule` declares an ID, version and synchronous registration function. A module registers `ToolExecutor` instances through `ToolRegistry.registerModule`. Registration is validated and atomic: duplicate names, conflicting modules or invalid category declarations cannot partially install a module. Model tool schemas come from this same registry. Built-in files, questions, repositories, project Tools, Git, changes, memory and workflow are registered as modules through this contract.

An executor declares `ToolAccess`: named categories with initial Allow / Ask / Deny decisions and a deterministic classifier over its validated arguments and prepared data. Missing declarations receive one generic Execute/Ask category. Tools do not write their own permissions; they declare defaults and classify actions. The application composes `ToolPolicies` as the generic `Policy` implementation. The default-only in-memory implementation exists for embedding/tests. The old name-based InitialPolicy dispatcher has been removed.

New projects and newly opened projects provision `tools/builtin.<functionName>.json` and a registration catalog. Each manifest contains identity, implementation binding and policy. These are independent project copies, not inherited mandatory rules. New tools and newly declared categories are added automatically; existing choices are preserved even if module defaults later change. Removed modules are no longer exposed and old files remain intact. Installer/package discovery is deliberately not implemented; future trusted modules can use this registration contract without adding cases to the policy engine or UI. This contract does not isolate arbitrary third-party backend code: installing such code will require its own trust and lifecycle design.

Policies are edited inside a tool in the main-area Tools catalog or directly in its manifest JSON. There is no separate Policies view or policy RPC. Each action loads the current saved manifest. Missing, malformed or incomplete known policies block the tool and are not silently repaired. UI saves use expected file revisions to reject stale drafts. External file edits therefore affect subsequent actions without a backend restart. The catalog is bookkeeping, not a second permissions source.

The runtime records category, decision and a revision bound to policy content plus module identity/version and categories. Action approval fingerprints include this authorization stamp. Immediately before execution the engine reevaluates it: a changed policy invalidates the prepared action rather than consuming an old permission. Deferred proposal persistence is also checked against current policy before its response handler writes files. Human question/step/proposal interactions and executor workflow/path guards remain separate from access decisions; Allow never manufactures their approval.

The universal Git categories are Read, Local/Other, Network, Publish and Destructive. Only a conservative set of state-inspection commands is classified as Read; other supported built-ins default to Ask. Destructive classification is a review aid, not a proof that other commands are harmless. All mutations are reviewable by default. User-configured Allow permits automatic execution; Deny blocks it. The chat shows the literal arguments, current branch, clean/dirty state, category and warnings before an Ask action.

Git invocation fixes the canonical registered work tree and Git directory and binds the executable digest, source/HEAD/branch, configuration, refs and index before execution. Changed state invalidates a prepared mutation. Branch switching additionally requires a clean tree and no ongoing merge/rebase. Existing workflow branch bindings cannot be bypassed with generic Git plumbing; unprepared workflows use the original scoped branch tool before source/history changes. Task-scoped stage/commit-like mutations still require a permitted ready step and approved ChangeSet paths.

This is a constrained host Git adapter, not arbitrary Git plus OS filesystem isolation. Repository-management/configuration commands, aliases/plugins, path overrides, external drivers, command-executing bisect/rebase options, signing handlers, interactive editors, submodules and unsafe link operands are rejected. Configured custom filter/diff/merge drivers require manual resolution in this version. Existing saved rebase exec instructions are rejected. Global/system Git configuration, automatic credential helpers, hooks, pagers and automatic maintenance are disabled. HTTPS/SSH are the supported network protocols; no credential broker is added. SSH may still use the user's installed SSH configuration. Missing credentials cause a failed command rather than an interactive prompt.

Native commands have closed stdin, a two-minute Git timeout, bounded output, cancellation and process-tree termination. Results record exit status separately from text and are never inferred from a user saying an action was done. They are ordinary host processes; these guards do not promise isolation against hostile native software or filesystem races. Native configuration controls and built-in discovery were checked against the [Git documentation](https://git-scm.com/docs/git) and [Git configuration reference](https://git-scm.com/docs/git-config).

Edits revalidate registration, canonical repository paths, directory/file types, non-linked files, original SHA-256 and prepared content immediately before saving. Task-owned edit digests are persisted: unrelated changes after branch preparation or concurrent edits to task-owned files block further writes. Linked/hard-linked, Git metadata, binary and oversized files are rejected. Replacements use temporary files plus rename; creates support checked parent-directory creation. This is path containment and optimistic source checking, not an OS process sandbox against a hostile local user concurrently rearranging the filesystem. Outside edits cause conflicts rather than a blanket overwrite. Interrupted mutations are not replayed automatically.

ChangeSet plans include a generated scope header with repository IDs, exact writable files and optional agreed base branches. A plan's digest excludes its separately delimited execution notes. Notes therefore do not invalidate plan approval, but changes to plan content or scope do. Digest-based updates reject stale source documents. Material plan changes require reopening/reviewing the plan step.

There are no dedicated SSH, Kubernetes, database, commit/push/deploy tools, local-model reviewer or credential broker in this slice. Local check execution is a trusted host capability requiring a concrete user permission, not a filesystem isolation mechanism.

## Project Tools, policies and executors

The three layers are separate: project tool definitions describe capabilities; project policies decide Allow/Ask/Deny; installed execution adapters do the work. Checks is no longer an active service, folder, UI section or model tool family. Verification commands are ordinary tools.

A schemaVersion 2 manifest in `tools/<id>.json` contains a stable id, toolName (model function name), name, description, implementation {executor, configuration}, and policy {category: allow/ask/deny}. `ProjectToolRepository` validates implementation and access categories through `ImplementationRegistry`, without branching on provider IDs. Policy evaluation, implementation binding and execution remain separate interfaces even though their configuration is one document. Saving validates project scope but does not require installing or running the command. Each adapter declares its configuration schema, scope validation, preparation binding/review, resource identity, output bound, execution and optional source-evidence comparison. `LocalProcessExecutor` is the initial adapter; arbitrary backend-code installation is not provided.

`tools_list`, `tools_get` and `tools_propose` manage definitions. Proposing returns a typed `tool_proposal` interaction, preserving the originating run/tool call while the user edits and approves/rejects the definition. Creating or updating it never executes it. The approved result includes a functionName, revision and executed:false. Before the next model turn, the registry loads that project's current definitions and exposes each as its own callable function. Native-process tools store a fixed command without a repository binding. Each invocation selects a registered repository by ID. The executor checks the registered link and canonical working folder both at review and before launch; the reviewed repository is recorded with the run. Runtime inputs cannot override the saved command or working folder. Handler tools inherit the installed handler input schema, prepare/execute/respond lifecycle, interactions, availability and path/workflow guards. The model invokes the returned functionName with that declared schema. No generic unreviewed run-command shortcut exists.

Project registrations are keyed by canonical project. Only validated manifests are callable; missing or invalid built-ins never fall back to the raw global executor. Tools from one project never appear in another project. The main Tools catalog provides search and All / Built-in / Project filters, clickable rows, a detail editor with embedded access rules, Open JSON, manual review/run for process tools and process execution history. Unsupported handler bindings remain visible as unavailable. New projects create tools/; the old Checks view and API bindings are removed.

Each tool manifest embeds its own policy. Native execution initially uses Execute/Ask; installed handlers declare their own categories and defaults. Editing any manifest field changes the full-document revision used by policy authorization fingerprints. CAS saves protect concurrent edits. Native and installed-handler implementation providers share the same manifest lifecycle. Prepared permissions additionally bind definition content, adapter preparation, registered roots, source identity, executable and relevant environment. Changed policy, definition, binding or source invalidates a prepared action. Missing, malformed or unsupported definitions are not callable. Invalid policies still fail closed.

`ToolExecutionService` orchestrates runs through an installed `ExecutionAdapter` and records them in `~/.governed-ide/runtime/executions.sqlite`, partitioned by canonical project and linked to the originating task. It serializes launch checks for the adapter's resource identity, bounds captured output, exposes Stop/history and never automatically replays interrupted jobs. Adapters supply a review rendered generically by the UI. Manual runs keep output local; model invocations return at most 12,000 output characters with truncation and provenance flags. Secret filtering remains disabled. Tool creation approval does not imply execution permission; subsequent invocation follows the capability's own policy.

The local-process adapter starts a native executable with literal argv, shell:false, closed stdin, a timeout, bounded stdout/stderr and process-tree cancellation. It inherits only PATH, locale, temporary-directory/platform essentials and an application-specific home/cache. Broad credential/proxy environment and the user's home configuration are not inherited. Missing executables are reported without installation; Windows .cmd/.bat wrappers require a native executable or Node's JavaScript entry point. macOS execution is tested; no claim of Linux/Windows runtime verification is made here.

Working-folder containment is not OS filesystem/network isolation. Local commands can access host files, execute repository code and contact the network with normal user permissions. No classifier or local-model judgment is treated as an isolation boundary. Detached malicious descendants and hostile filesystem races are outside the process-tree guarantee. Before/after source observations cover tracked and non-ignored regular source contents/modes and link paths, not ignored dependencies, external link targets, or transient changes reverted before the final observation. Source changes or unavailable after-state are flagged rather than presented as final-source verification.

### Installed handlers and future extensions

`ToolModule.register` may call `registerHandler` with a stable ID, apiVersion, settings schema/defaults, validation and a bind(settings) factory returning a ToolExecutor. Ordinary built-in executors are automatically exposed as handlers under `<moduleId>/<functionName>` with the module major API version and no settings. An explicit custom handler can have settings and runtime arguments without installing a default project tool. New projects copy manifests for globally registered built-in executors.

A handler manifest uses `implementation.executor: "handler"` with configuration `{handler: "module/handler", version: "1", settings: {}}`. Handler IDs resolve only against already installed code. Unknown IDs or API versions are unavailable; JSON cannot name an import path, evaluate code, fetch a package or install software. The same installed handler can back multiple project tools. Runtime actions retain canonical handler identity so aliases preserve compact file-read rendering and memory evidence. Native commands use `implementation.executor: "local-process"` with the fixed command configuration.

Third-party discovery/install/update is intentionally absent. A future installer must separately establish package trust and lifecycle, then register modules/handlers/execution providers through these interfaces; copying a JSON manifest only enables already installed implementations. Backend extensions are trusted application code, not isolated by policy. Policy Allow does not remove technical path restrictions or required workflow/user interactions.

## Durable selective memory

Project Context contains only researched repository summaries, topic cards and source references. Ordinary tasks automatically receive a compact index (approximately 5,500 characters), not all topic bodies or all source files. The agent selects relevant topics.

Memory contains durable current architecture, responsibilities, contracts and reusable patterns, supported by current source. Task status, test execution results, run observations, intermediate plans and verification reports belong in ChangeSets/history. Explicit task-activity formulations are rejected, and changes to existing memory are reviewed. These controls do not guarantee perfect semantic classification of arbitrary prose.

Topic IDs are architecture, modules, data, integration, patterns, testing and operations. Each card is at most 4,500 characters, eight facts, three examples and four architecture unknowns. New facts/examples must cite files actually read successfully in the task. Code copies, fences, oversized prose and invented evidence are rejected.

Publication merges with the saved map: unrelated topics and existing facts remain, duplicate facts/examples are consolidated, and bounded lists are never silently truncated. An obsolete fact, example or unknown requires explicit retirement by its exact saved key. If a merge exceeds bounds, it fails and asks for deliberate consolidation. Read generations provide optimistic concurrency; changed source evidence or changed memory prevents stale publication.

Existing-memory research refreshes read affected saved topics and submit one final proposal, reviewed in Project Context without exposing a user research chat. Normal tasks can use context_update for a reviewed minimal update. No durable change is a valid outcome: skip the write and record that decision in the ChangeSet/step result.

The active snapshot uses generated JSON and a readable Markdown companion under `context/memory/repositories/<id>/`, with an atomic index pointer. Superseded snapshot pairs are removed after publication; only the final active pair is retained. Failed/cancelled pre-commit publication leaves the prior map intact and cleans temporary files. Execution audit history remains in SQLite. Freshness checks compare registration, local Git state and referenced source hashes. They do not establish an exhaustive repository audit.

## Interaction and model-turn contracts

`InteractionRequest` is persisted independently in SQLite schema v3. Its kind is `question`, `tool_proposal`, `workflow_approval` or `action_approval`; its state is pending, answered, cancelled or invalidated. Each request has an immutable key and links to its task, run, originating action and/or step revision. Runs and workflow snapshots store the ID they are waiting for.

`ask_user` returns a typed question outcome. The runtime persists the request and pauses the run; it does not complete the tool call until the real user answers. `respondInteraction(id, response)` is the only frontend response API. Questions accept an option ID or custom text. Workflow approvals bind the reviewed revision and artifact digests; action approvals bind the existing argument/target fingerprint authorization grant. A question response cannot grant either kind of approval. Repeated identical responses are idempotent; stale or conflicting replies fail without advancing execution.

The provider adapter explicitly emits a `message` or `actions` outcome. Execution records turn outcomes as message, interaction, step result or blocker. Ordinary Chat permits a terminal message. Executing workflows and Auto routing declare allowMessage: false; the OpenAI adapter requests tool_choice: required, so a turn must include an action, question, step result or blocker. Narrative text may accompany a tool call but cannot end workflow execution. An out-of-contract provider response fails visibly without retries. Previously paused message-only runs remain resumable through Continue; their workflow step is preserved. There are no content-based question detectors, hidden correction prompts or automatic protocol retries. Tool schemas and normal input validation define the protocol; model instructions require questions through `ask_user`.

Only current manifest, workflow and database formats are accepted. Runtime services do not import prior Checks databases, archive former policy files, convert older tool/workflow schemas, or import browser preview chat history. Project identity lives in project.theia-workspace. Unfinished current executions are interrupted on restart and never replayed.

## Persistence, recovery and UI

Runs/actions execute sequentially; a model workflow-control call must be the sole tool call in its response. Action approvals bind tool arguments and prepared target/content data. Step approvals bind result revision and plan digests. Browser reloads preserve both. On restart, in-flight runs/actions are marked interrupted and require explicit continuation; pending reviews/approvals remain saved.

Repository research jobs are excluded by the user task-list API, including failed jobs. Project Context shows their state, stop controls and final memory review. Ordinary chat tasks remain separate.

Chat stays pinned first. Consecutive file reads are grouped in a compact filename/status block; frontend snapshots omit raw source-read payloads. Other tools have expandable results. The workflow panel shows current stage, questions/blockers, reviewed results, artifact links and completed-stage summaries. Results render after a provider response; token streaming is not implemented.

Secret heuristics remain disabled at the user's request. Messages, source reads and results are not redacted for credentials. Size, UTF-8 and path checks remain; accessible credential-like content can reach the external model. No new secret filter was introduced by the architecture-memory content rules.

## Verification

With the bundled Node 24 toolchain on PATH:

```sh
yarn --cwd theia-extensions/product build
yarn --cwd theia-extensions/product test:harness
yarn --cwd applications/browser build
```

The automated tests use real temporary Git repositories, files and SQLite databases with a fake provider boundary. They cover clarification/recovery/approval, Auto routing, immutable snapshots, real plan→approval→branch→edit dispatch, dirty-state refusal (including new unrelated changes during implementation), cross-project shared-checkout locking, stale documents/source, registration changes, traversal, symbolic/hard links, redirected Git metadata/environment, memory merges/explicit retirements/review/final-snapshot retention, plus previous repository/file/provider/editor regression checks. They do not claim arbitrary criterion semantics or live account availability.

Live validation on a synthetic repository confirmed that ChatGPT asked for a missing numeric value, paused the same step, received an answer and requested explicit approval. After a real IDE approval receipt, it discovered/read the repository, inspected Git, saved a correctly scoped Markdown ChangeSet and paused for its review without modifying source. Clarification questions and step reports remain in the chat; internal approval receipts reach the provider while the UI shows a concise approval acknowledgement. Workflow control calls are represented by the progress panel rather than additional tool rows. Source-edit payloads, like source-read contents, are omitted from UI polling snapshots.

## Tools with methods

Installed modules can declare a ToolFamily referencing their installed executors. Project provisioning creates one manifest per family: Git, ChangeSets, Context, Repositories, Workflow, Tools, Files and Executions. Handler implementation IDs remain internal bindings; individual method names are not registered as separate callable project tools.

The generic `methods` implementation composes 1–40 named methods. Each method declares id, display name, description and an implementation binding. It can use an installed handler or an execution adapter such as local-process. Methods cannot contain nested method groups. A package can reuse one installed handler ID with different validated settings for its methods. No code imports, evaluation or installation are driven by a manifest.

A family is called as `git({call:{method:"status",arguments:{repository:"back"}}})`. The schema contains a discriminated branch for each currently permitted method and its own input schema. The runtime normalizes the arguments, persists the method identity and canonical handler operation, and binds the method into action permission fingerprints. Questions, workflow transitions and tool proposals retain their original interaction semantics; the control/interaction flags are selected by the actual method rather than the family name.

The single manifest policy uses namespaced keys such as `status--registered-git-read` or `command--network`. Rules are edited inside the selected method in Tools. A method whose categories are all Deny is omitted from model schemas and blocked at dispatch. Category-level rules remain available for commands such as Git. Definition revisions cover the entire manifest, including all methods and policies.

Workflow selections reference a whole family (`builtin.git`) or individual methods (`builtin.git#status`, `builtin.git#diff`). The editor displays one added family with method chips. Provider schemas, runtime scope checks and workflow capability checks use the same filtered method set. Core ready/report/revise methods remain available as workflow support, subject to policy. New methods are not implicitly granted to an explicitly selected subset.

Workflow.request_tools is a workflow support method for explicitly requesting missing installed methods in the current task step. It creates a durable workflow_tools review, separate from ordinary questions. Approval adds only the reviewed references to the active snapshot, increments its revision and clears readiness; the same run resumes with updated schemas. It never edits project workflow definitions, tool policies, approved plans or branch records. Full-family requests expand to the currently enabled methods rather than granting future additions. Reviews bind step revision and tool manifest revisions; unavailable/denied methods, stale reviews and cancelled requests cannot grant access. Denial leaves the selection unchanged. Tool policies and mutation guards still run on every subsequent invocation. The Development Git-preparation template includes ChangeSets.notes because its completion criteria require recording actual branch/base details.

When an installed built-in module adds a previously unknown method, project manifest initialization appends that method and its default policy. Existing names, descriptions, implementations and policy decisions remain intact. Existing workflow subsets are not expanded automatically.

Tools.propose accepts a complete manifest as a JSON string and an expected revision; the repository performs implementation, policy and path validation. This keeps installer schemas out of every model turn. Tools.implementations explicitly discovers installed implementation choices and their configuration schemas. Saving a proposal never executes it. Manual native method runs retain preparation review, revision binding, job records, cancellation and source observations.

## Database-backed task context

The existing messages/actions/interactions journal is the source of task history. There is no second conversation store, no project context files for task summaries, and no user-visible system summary task. SQLite task schema v6 adds task_results and task_checkpoints. The preceding schema v5 is upgraded in place without deleting messages; other historic database schemas remain unsupported. Existing result payloads are normalized losslessly on access. A task-scoped content hash identifies one immutable result text shared by the action and its tool-result message. Public store reads hydrate results for existing evidence/approval consumers. Executions retain their own canonical job records; returned task observations remain distinct from the full execution record.

Checkpoints contain a bounded structured synopsis (goal, requirements, decisions, progress, verification, open questions, next steps), source references, a covered-through message ID, the covered-prefix digest, version and previous-checkpoint link. They do not copy raw messages/logs/code. The complete journal and canonical results remain readable after checkpointing. Workflow state, recorded task branches/edits, approved artifact digests and tool permissions continue to come from the engine, never from a synopsis.

TaskContextManager is composed from TaskSummarizer, TokenCounter and TaskResultView interfaces. The default summarizer calls the existing external ModelProvider with only a non-executable submit_task_summary schema; its responses never enter action dispatch. It merges the previous synopsis with a bounded additional history segment. Field lengths, token budget and task-local evidence references are validated before an optimistic, transactional commit. Concurrent appends remain in the fresh tail. Changed covered records or a competing checkpoint reject the commit. A stale recovered checkpoint is excluded and rebuilt from the original records. Cancellation/provider/protocol failures preserve history and the previous checkpoint; Continue retries preparation, not old actions.

The default operating budget is 64,000 baseline tokens with 16,000 reserved for response/reasoning and 1,024 additional framing tokens. o200k_base BPE is explicit, not a claim about the maximum or exact tokenizer of an account's dynamically selected model. The counter, operating budget and context manager are replaceable at composition time for other providers. Instructions and the actually selected method schemas count toward the budget. Preparation is checked before every model request; it starts checkpointing around 75% of the available input budget and aims for 50%. Summary batches and output have independent limits. Input measurement is incremental and does not construct/tokenize an unbounded complete result history.

The first user request is pinned, the checkpoint carries older context, and recent messages retain their original continuation items. Checkpoint boundaries never split a pending function-call/result batch. Large results have explicit bounded transport views and resultRef links; command status, exit code and output precede bulky source-observation metadata. Nothing is silently labeled complete from an excerpt. If immutable instructions, current input or an indivisible recent batch cannot fit, the run stops with an explicit context error rather than dropping a user decision or reporting a generic connection problem.

Task Memory is one project tool family with search, read, read_range and read_result. Every handler derives task ID from the runtime context, verifies its project, and restricts queries and result IDs to that task. There is no caller-controlled task/project selector. Replies use bounded excerpts and character-offset pagination; full results can be recovered without executing the originating tool again. Opaque provider reasoning is not exposed by retrieval. Policies remain editable per method, including Deny. Retrieval is workflow support subject to these policies and is excluded during initial workflow routing.

Summaries are model-authored and can omit or misunderstand facts despite structural/source validation. Original evidence is retained for recovery; a summary is never an authorization grant or proof of successful verification. This is separate from durable architecture memory. Provider protocol guidance: [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction), [reasoning context](https://developers.openai.com/api/docs/guides/reasoning). The implementation uses the provider abstraction and does not require a subscription to expose a native compaction endpoint.

### Docker tool

`builtin.docker` is one installed handler-backed tool with `connection`, `read`, `build`, `run`, `exec`, `push`, `remove` and `manage` methods. Policies live in `tools/builtin.docker.json`; workflow selections reference individual methods. The command classifier validates the requested method independently: reads default to Allow, build/run/exec/publication to Ask, explicit container deletion to Ask, and deletion of images/volumes/links, bulk pruning and other operations to Deny. Build exports and cache publication use the publication method; Buildx/plugins and builder overrides use Manage. Unknown operations never inherit read permission.

The Docker module resolves the native CLI and current Docker context or DOCKER_HOST on this computer, including Unix/rootless sockets, Windows named pipes and TCP/SSH contexts. Optional machine-only settings in `~/.governed-ide/connections/docker.json` accept schemaVersion 1 and program/context/host/configDirectory; project manifests contain no computer-specific socket. Explicit machine settings take priority. The module uses Docker configuration/authentication and a restricted Docker-specific environment; the generic local-process executor retains its isolated home. Before approval it records the executable/connection identity, exact argv, registered repository and source fingerprint. It revalidates these before spawning without a shell, serializes repository operations, bounds output/time and records the actual result in the existing task action journal. A connection/source change revokes the reviewed action. The `remove.containers` policy accepts only explicitly named containers and optional force removal, with at most 20 targets; other removal forms use `remove.execute` (Deny by default). Before review, read-only container inspection resolves full IDs; execute rechecks those IDs and removes by full ID rather than name. Container replacement invalidates approval. Cleanup does not delete volumes. This permission is not an ownership proof: the agent must use unique task-owned verification containers and the user reviews each exact cleanup command. This is normal Docker access, not host isolation; CLI cancellation does not guarantee daemon-side cancellation. No automatic installation, daemon startup, login or socket fallback occurs.

Docker provider tests cover macOS, Linux/rootless, Windows, TCP/SSH, precedence and invalid configuration. A real macOS read-only query reached Docker Engine 29.1.3 through the selected desktop-linux context. Linux/Windows execution has not been verified on physical hosts. The old Docker build manifest and intermediate connected-process implementation were removed; historical executions remain audit records.
